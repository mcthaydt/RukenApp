# The staged path

- **When.** Stage the work when the outcome or the approach is uncertain, when it waits on an open decision or on other work, or when it is lane 3. A new feature or many files alone does not stage it. Risk decides the audits, never the number of tasks; the audits for each lane are in Settings.
- **Can this runtime start sessions?** Before the first stage, the coordinator checks each capability on its own: starting a session, sending it a message, choosing its model and archiving it. A missing one changes only what needs it: without archiving, finished sessions are listed for the owner to close; without a model choice, sessions run on the default; without messaging, sessions report through committed files. Reviews run in fresh, isolated sessions wherever the runtime can start one (a new session, or an isolated reviewer it supports). The coordinator asks the owner to start a reviewer only when no isolated reviewer session can start, and then runs the stages one after another itself, each starting from the committed documents.
- **Superpowers.** Its skills run the steps named below (brainstorming, writing-plans, executing-plans), at the version the setup check records; where they differ from these rules, these rules win. Its `test-driven-development` and `verification-before-completion` are read with Verification in `build`. A final review its skills ask for is the implementation audit when the lane calls for one, run once by a fresh session (`review`), not a second review; on lane 1 it is the implementer's own check. Any deferring minor findings it suggests does not apply: the fix round fixes every in-scope finding.
- **Splitting.** Split by what a mistake costs, not by folder: one unit, one input, one output, one lane. Each unit is a row in the plan: its name, the units it waits on, the files it owns, its output and its acceptance check; its status is in `progress.md`. A unit waits on another when it reads that unit's output, or when the two touch the same file, interface, schema or assumption, and no two running units own the same file. Units inside one implementation pull request run in plan order on its branch; across pull requests a unit starts from a `main` that holds what it waits on. Units that share none of those run side by side. An order written in a plan is a claim that one unit waits on another, checked against those, not a queue: units that share none run side by side up to the writer limit in Settings, and a plan that starts a unit "after the previous merges" names what it reads from them. Each unit runs its own produce, check, correct loop; what it waits on decides only when it may start. A step with one right answer (merge, rank, dedupe, compare) is plain code, not a model. Build the gate first: before a repeated job, write the one check that can fail it.
- **One working brief, one implementation pull request.** On the staged path the brief is the spec: the outcome, the acceptance criteria, the boundaries the owner approves (dependencies, tools, environments, budget, expected duration) and the plan, in one document. The spec and its plan audit are docs: the spec merges on green without the owner, with its plan audit when it has one, and the build starts from `main`. Execution, the implementation audit and the fixes share one branch and one pull request: the audit reviews that branch before it merges, and the fixes land on it.

| # | Stage | Who | Writes |
|---|---|---|---|
| 1 | Spec | A spec session the coordinator starts, with the owner (superpowers brainstorming); a plan session adds the plan when the approach is uncertain (superpowers writing-plans) | `docs/superpowers/specs/<date>-<topic>-design.md` |
| 2 | Plan audit | An audit session, `review` skill (lane 3 only), on the spec's pull request | `docs/superpowers/audits/<date>-<topic>-<cycle>-plan-audit.md` |
| 3 | Execution | The implementer: one work session (superpowers executing-plans) | the code |
| 4 | Implementation audit | A fresh audit session, `review` skill (lane 2 and 3) | `docs/superpowers/audits/<date>-<topic>-<cycle>-implementation-audit.md` |
| 5 | Fixes | The implementer, in the same session | the code |
| 6 | Review | The owner approves the finished result | notes for the next spec |

- **Writing.** One writer per branch at a time: the implementer writes, then hands the branch to the reviewer by naming a commit; the reviewer commits only its audit file and hands the branch back by naming its own commit. The audit reads a named commit, never a moving branch. Independent writers use their own branches or worktrees. The coordinator is the only writer of `progress.md` and `history.md` while active, including for delegated short-path work; each session's own live-state file in `docs/superpowers/live/` is the exception, written only by that session. If the coordinator cannot write to the repo, the implementer writes them for it and says so in the commit. Otherwise the implementer owns those records. The tracking document in the implementation prompt is the plan's own checklist, written by the implementer on its branch. Worker reports do not create additional writers of the shared progress record.
- **The coordinator** is one long-lived session. It talks with the owner, creates `progress.md` and `history.md` if missing, starts each stage's session, tracks them in `progress.md`, names each unit's lane in the spec, and archives each session when its job is done: a spec, plan or audit session once its file is handed back, and the implementer only after its pull request merges or it hands off under Session refresh, because the fixes are its job. An implementer or slice builder waiting on a review or the owner keeps its place among the 3 writers but does not count toward the 5. The coordinator never counts toward the session limit.
- **Specialist sessions start on demand:** a plan session, an audit session or the advisor starts when its work is ready and is archived when it is done. Nothing waits idle, except a writer waiting on a review or the owner.
- **The advisor** gives a short second opinion on a big call: the risks, what is missing, a recommendation. It never writes code or changes files. The coordinator starts it only for big calls: specs, plans, roadmap changes, and approving designs and layout sketches. It does not reopen the owner's decisions.
- **Slice end.** Every slice, the first one included, closes in this order: a fresh end-to-end walk (see `review`); the design review rounds before the owner's first look (see `visual-check`); the screens page, for the owner's first look; the round after it, on the owner's notes; the screens page again, for the owner's second look; the owner's own walk; and last the retrospective. Do not move to the next slice without a design review loop on the screens completed during that slice.
- **End-to-end walk.** A fresh session that did not build the slice walks every journey in it and reports each step as pass or fail, with evidence (see `review`). **Screens page.** All of the slice's screens in one organized artifact, grouped by flow and device, for each of the owner's two looks (see `visual-check`).
- **Retrospective.** The last stage of every slice, the first one included. After the slice ends (on the short path, after each approved finished result), a fresh thread reviews every loop the slice ran, not only design review: the build and fix rounds, the audits, the end-to-end walk, every review round, CI waits and stalls, flaky tests and repeat fixes. It turns each lesson into a test where it can, such as a PR-footer check, and proposes the rest as one rule-change pull request for the owner to approve. It also prunes, as Prune under Verification in `build` says. Nothing to learn, no pull request. The next slice can start once the retrospective's pull request is open, or once the retrospective reports nothing to learn.
- **Handoff.** Every stage reads the files its prompt names, normally the spec, the audits so far and `progress.md`; the plan also reads Lessons in `history.md` and carries those whose trigger its work matches. It reports its progress to the coordinator, which keeps `progress.md`, and its last step is to commit and push. `progress.md` holds the active milestone, including completed outcomes needed to understand what remains. When a milestone closes, its work and decision records move to `history.md`; screen approvals are recorded there with their scope. The execution session starts with this prompt, and uses it again for the fixes:

```
Use superpowers:executing-plans to carry out the plan, and develop by these instructions.

Now implement precisely as planned, in full.

Implementation Requirements:

- Write elegant, minimal, modular code.
- Adhere strictly to existing code patterns, conventions, and best practices.
- Keep comments brief, and only where the code doesn't explain itself: say why, not what.
- As you implement each step:
  - Update the markdown tracking document and overall progress percentage dynamically.
```

- **Reporting.** Workers report to the coordinator through `send_message`, or committed files when messaging is unavailable: the task as understood at the start; meaningful milestones and their evidence; material decisions and assumptions; deviations and their reasons; previews; blockers; and completion. Separate facts from estimates and owner instructions from agent-selected choices. Ordinary debugging stays internal unless it changes outcome, timing or confidence. A missing tool replaced by an authorized alternative that meets the same acceptance criteria is a deviation, not a stop; an access refusal is never worked around.
- The session that merges reports each merge and each stop listed in `release`. Coordinators of related workstreams report decisions, changes that affect this work, blockers and what they push. The coordinator keeps the owner informed under "Owner visibility and early steering", including decisions that need no approval. Pause and request an owner decision only when the brief, permissions or an unresolved choice requires it; keep independent work moving.
- Each session's prompt names the files to read. A session watching CI reads a log only when a check fails, and waiting does not suspend the owner update interval.
