# Release

## Setup check

The first session in a repo runs this first, before it builds anything, and again when the CI, the runtime or the superpowers version changes. It verifies each item, sets up what is missing with the owner's authorization (CI workflow files are lane 3, except at first-time setup: see Risk in CLAUDE.md), and reports each one as present, added or missing:

- Every step only the owner can run (creating the repo, branch protection, credentials, and anything the sessions lack the access for, such as deleting branches), listed as one batch of CLI commands before building, so the owner is not needed mid-run.
- The commands in Stack and checks (CLAUDE.md) run, and pass on `main`.
- The CI gate described below: the workflow triggers (with `ready_for_review` on a public repo), the job that decides which checks apply, and the final aggregate gate job.
- The gate is required by branch protection on `main`, which keeps every existing required check unless the owner authorizes its replacement.
- Branch protection on `main` does not require branches to be up to date before merging, and every push to `main` starts a full run that no newer push cancels.
- The merge queue (see Lanes and merging): GitHub's, turned on for `main` where the repo can have one, with the workflow listing the `merge_group` trigger and the queue's merge method set to a merge commit; or reported as not available, so the session that merges runs the queue by hand.
- Whether the repo is indexed in Graphify, found or missing. When it is, every session's prompt says so, and every thread uses it (Limits in CLAUDE.md).
- A `commit-authors` check inside the gate: it fails a commit not authored and committed by McThayDT <107786093+mcthaydt@users.noreply.github.com>, a Claude co-author or "Claude-Session" trailer, and a pull request body that does not end with "Requested by **McThayDT**" or that carries a "Generated by" or "Generated with" line. It reads only the pull request's own commits, and runs again when the body is edited.
- When the owner names a restart handoff (copies of a repo's rules, CI workflows and settings kept before they were removed), the CI, the gate and the repo's own notes are restored from those copies first, as first-time setup (Risk in CLAUDE.md), and the branch protection goes into the owner's batch of commands; each is reported as restored or changed with a reason, before anything new is written.
- Whether the repo allows auto-merge (`gh api repos/<owner>/<repo> --jq .allow_auto_merge`); a private repo on GitHub's free plan cannot. Also whether it deletes merged branches by itself (`delete_branch_on_merge`).
- The session tools the staged path uses (starting, messaging, choosing a model for and archiving sessions), each found or missing.
- The superpowers version, recorded as a commit or release under "Setup" in `docs/superpowers/progress.md`, and any place its skills disagree with these rules.
- The compaction hook: `.claude/settings.json` has the `SessionStart` entry with the matcher `compact`, and its command prints `.claude/after-compaction.md`.
- The rule hooks: `.claude/settings.json` runs `.claude/hooks/rules.mjs` on `SessionStart`, `PreToolUse`, `PostToolUse` and `Stop`; `node .claude/hooks/rules.mjs --check` reports no blank left (it reads the author and the "Requested by" line from the Identity rule in `CLAUDE.md`); `.claude/hooks/rules.json`, whose repo values (render commands, software-renderer variable, design tools allowed to take screenshots, required statuses, session and message tools, hosted-runner check on a private repo, `firstTimeSetup` turned off at the end) the setup check fills in, also holds the pull request flow check (a lane and acceptance criteria in the body, drafts, the open pull request limit, a passing review naming the head commit before a lane 2 or 3 merge) and the subagent model check; a fresh session shows the rules at its start; and where sessions start one folder above the repo, `node .claude/hooks/rules.mjs --install-user` has added the launcher to `~/.claude/settings.json` on that machine, so those sessions load the hooks too (run it once on a computer; a cloud environment starts every machine fresh, so paste what `node .claude/hooks/rules.mjs --print-setup` prints into its setup script once: that script needs no repo and never stops a session from starting).
- The `verify` skill: `.claude/skills/verify/SKILL.md` is there, and a fresh session that follows it from a clean checkout starts this repo's app or game in a cloud container and gets a screenshot of its main screen. In a repo with nothing to start yet, it is reported as missing until the first screen exists.

## Where work runs

Choose where work runs by what it needs, not by habit.

- In the cloud: anything a container can do, including a headless browser for screenshots and browser tests, logic, tooling, unit tests, docs, long work nobody steers minute by minute, the coordinator, plans and audits.
- On the owner's computer: only for a private repo, and only what needs real hardware or the owner's hands (a GPU, a physical device, real input feel), under a standing permission for that machine.
- On a public repo no session runs anything on the owner's computer: no test, build, app, game, measurement or command. What only the owner can run goes to the owner as CLI commands. What needs real hardware is measured by the owner by hand, for example on the deployed preview, from steps the session writes out, and until then it is reported as not measured, never as met.
- Browser device profiles emulate a screen size, a user agent and touch. Their results are emulation evidence, not proof of performance on a physical device; a budget for a device is measured on that device.

## Where tests run

- Quick targeted tests run locally whenever they help, before you push: the checks for what changed. Locally means where the session runs. On a private repo that can be the owner's computer, where they run one at a time, because two heavy jobs on one machine starve each other and fail on timeouts.
- On a public repo, tests run only in cloud containers and in CI.
- CI is the merge gate, and full suites run there. Checks for independent pull requests run at once, within the capacity in Settings; only the final integration with `main` runs one at a time. A repo with no CI workflow uses the host's build check, and a cloud session passes lint, typecheck and the unit tests in its own container before it pushes.

## Where screenshots go

- This section is for private repos. On a public repo, GitHub's artifact storage is free and has no limit, so a run there keeps its screenshots in GitHub's artifact storage, and of this section only the bullet that starts "On any repo" applies.
- On a private repo, CI screenshots never go to GitHub's artifact storage: not the screenshots a run takes, not a browser report that carries them, and not the expected, actual and diff images of a failed visual comparison. There, that storage is shared by the whole account, limited, and counted as an average over the month: a delete stops further charges but does not bring the month's figure down, and once the account is over its included storage, every upload fails, on every pull request, until the month resets.
- They go to a private object store outside GitHub, with a key that reaches only that store, and the run summary links them; the links run out when the pictures do. A scheduled job deletes each one a few hours after upload, and a lifecycle rule on the store deletes anything the job missed soon after, as the backup. The store, its rule and its key are made at the setup check, in the owner's batch of commands. The upload step and the cleanup job are CI workflow files, so a change to them is lane 3 (Risk in CLAUDE.md).
- A run with no key, such as a pull request from a fork, which gets no secrets, skips the upload and says so in the run summary. It never falls back to GitHub's artifact storage.
- They are short-lived by design. A reviewer or a screens page that needs them after they are gone shoots them again on the named commit, on the set "Shoot what the change touches" in `visual-check` names. Nothing keeps a longer copy, in the repo or on GitHub.
- On any repo, the screens page carries its own copies of the pictures it shows, since links into a run's storage run out, and only until the owner has looked at it (Screens page in `visual-check`). A session's own screenshots for its own check stay in its scratchpad (`verify`).
- The check, on a private repo: a test reads the workflows and fails on a step that sends screenshots, or a report that carries them, to GitHub's artifact storage. Trigger: a diff that adds or changes a screenshot upload.

## Fast CI (public repos on GitHub's runners)

- Open every pull request as a draft; the implementer marks it ready for review as its last step, after its final push and after every review its lane calls for. Private repos use no draft rule for lane 1.
- A draft gets a quick run: lint, typecheck and build in full, but only the tests the change reaches, stopping at the first failure.
- Marking the PR ready starts the full run used by the merge gate, but only when the workflow lists `ready_for_review` in its `pull_request` types: the default types (opened, synchronize, reopened) do not include it. Check the workflow file before relying on it. Green on a draft is not done.
- Screenshots and playtest video are taken automatically when the diff touches screens, scenes or gameplay files (the workflow lists those paths), with no label needed, and only of the screens those files reach, at the sizes they affect (`visual-check`).
- Browser tests run in the pieces set in Settings (CLAUDE.md), with the browsers in the job's image and installs cached (Making CI fast, below). A newer push to a pull request cancels its older run. A run on `main` is never cancelled, so every merge gets its own result. A change to the database, fixtures, lockfile or build/test config makes even a draft run everything.
- Watch the run in the foreground until it ends (`gh pr checks <number> --watch` or `gh run watch`, with a long timeout, repeated until the run ends), and never end the turn to wait for it. Act the moment it ends. Read a log only when a check fails. Where `gh pr checks` fails because GitHub's GraphQL API is blocked (some cloud sessions), poll the REST API in one foreground loop instead: `gh api repos/<owner>/<repo>/commits/<sha>/check-runs`, every minute, until no run is queued or in progress.

## Making CI fast

- The aim: a pull request gets its result in under 1 minute at the median and under 2 minutes at p95, without letting CI lie. Three rules come before speed:
  - The full suite runs before anything reaches `main`. Selection only narrows a pull request's feedback.
  - Never hide a failure. No retries, wider timeouts or skipped tests. A check that needs a retry has a bug: find it. The one exception is main's browser journeys, which CI tries up to "Retries on main" in Settings so a flake does not hold the deploy (owner, 2026-11-27); a test that passes there only on a later try is still a defect, listed in the gate's run summary, and the session that merges records it. Pull request runs and sessions never retry. The one rerun `build` allows to find out whether a failure is flaky is a diagnosis, reported with both results, never a pass; a gate retrying an outside service's call that answered 429 or 500 is not a check retry.
  - Never check less. Lint rules and required checks only stay or grow.
- Audit first, at the setup check and whenever the median misses the aim: pull the last 150 runs and split every job into waiting, setup and running, at p50 and p95. Fix the biggest bucket first.
- The toolchain is the one the Default stack names: one fast tool each for tests, the typecheck, lint and formatting, with every lint rule on that can be. A tool that exists only in a canary is pinned to that exact canary. A repo that already has other tools keeps one only for a measured reason: before each switch, run old and new side by side and list anything the new one misses.
- The shape: lint, typecheck, build and tests run in parallel, and no required check waits on another; only the final gate job (Docs only, below) waits, to collect them. Shards are filled by the test times that `main` records on every full run, and the shards together are shown to have run every file. Until a pull request is marked ready, it runs only the tests the diff can reach; the full run that gates the merge runs everything (Fast CI, above). The workflow lists the inputs that rerun everything (the lockfile, build and test config, shared fixtures, CI files), and when selection is set up, a real change hidden from it on purpose must turn CI red. The backend the tests drive builds the app once per test process, not once per test file. Match workers to cores before raising the pieces in Settings.
- Public repos keep GitHub's own runners, which are free there, for the jobs Where tests run puts on them. Nothing a job can be given ready-made is installed in it: a job that drives a browser runs in an image that already holds the browsers, pinned by digest to the locked version (Default stack). Installs are cached from `main`, and a slow job that only takes pictures stays off the path to the required checks.
- One small pull request per change, with before and after numbers from real runs. Do everything you can without the owner first; bring anything that needs an account, a secret or money as one list with its expected monthly cost. End with total CI time and cost, before and after.

## Docs only

A pull request that changes only `.md` files is lane 1, and its tests may not apply, but its required check is never skipped: a required workflow skipped by a path filter stays pending, and a job skipped by a condition can report success without proving anything. So the workflow always runs. Its first job decides from the diff which checks apply, and one final aggregate gate job, required alongside any existing required checks, passes only when every applicable check ran and passed and every other check was marked not applicable by that first job. Specs, plans, audits and progress notes are docs, so they merge on green without the owner, and the next stage starts from `main`. Any other file in the change brings the tests back. Classify by effect as well as extension: rules files (CLAUDE.md, the shared skills, and anything else that decides what needs the owner) are `.md` files too, but a change to them requires lane 3 checks and reviews plus the owner's approval or an applicable standing permission. As Risk in CLAUDE.md says, a repo's own `verify` and `this-repo` skills take the lane of the code change they describe. One edited alone is lane 1, unless it changes what needs the owner.

## Lanes and merging

Every unit carries a lane, classified from its diff and what the change does (see Risk in CLAUDE.md). The highest lane wins, and confidence never lowers it.

| Lane | What it is | It merges when |
|---|---|---|
| Lane 1 | Small and easy to undo | Green |
| Lane 2 | Wide: shared code, a schema, config | Green, plus the extra checks below |
| Lane 3 | Hard to undo | Green and its audits, plus the owner's approval or a recorded standing permission that covers it |

- Lane 3 never opens by itself.
- A lane 2 or 3 pull request goes ready, merges or gets auto-merge only when the newest verdict line (see "Checks and reviews" in `review`) on its head, or on a commit that reaches the head only through clean merges of `main` and notes-only commits, is a PASS. A merge of `main` counts as clean when its only conflict or hand edit is in `docs/superpowers/progress.md` (rules.json, `prFlow.notesPaths`); a notes-only commit touches that file and nothing else, a move onto or off it included. The hooks check this by diffing, so nobody judges it by hand (owner, 2026-11-27 22:23 UTC). A later FAIL on any of those commits wins until a newer PASS. The rule hooks refuse anything else.
- Ready for review means ready to merge: a repo may merge a ready pull request by itself the moment it is green, and that never waits for a review. So on any repo, public or private, a pull request stays a draft until the reviews its lane calls for are done: lane 2 until its fresh review, lane 3 (the rules files included, as Docs only names them) until its audits and the owner's word or a standing permission that covers it, and a spec until its plan audit when it has one. Lane 1 has no review to wait for.
- A golden that moves for an approved behavior change updates with the change, inside the scope of that approval (the spec or milestone that names it); one that moves only in a test or sample game merges on green. Each carries a before and after note in the pull request. Any other move of a golden in the shipped product waits for the owner. A golden is never re-recorded to hide a defect.
- A deletion the plan called for that git can restore merges on green, with a before and after note. Deleting anything git cannot restore is lane 3.
- Green means every required check is successful on the pull request's current head commit. The required checks are known in advance (the repo lists them): a missing, pending or unreadable check blocks the merge, and a new push makes earlier results stale. On a public repo the full run after ready for review is the one that counts. An audit or a visual review names the commit it examined and counts only for that code. A later commit that changes only the audit file, a live-state file or docs the audit did not cover keeps it. A commit that changes behavior makes it stale for what it touched: the checks that reach it run again and the reviewer reads that diff. A pull request that touches what people see is not green until its visual check is done and any fix it found is made (see `visual-check`).
- A merge queue keeps `main` green: before merging, integrate with current `main` and rerun the checks on the result, one pull request at a time and only the one about to merge. Use GitHub's merge queue where the repo can have one (a public repo owned by an organization, or a private one on Enterprise Cloud). Where it cannot, the session that merges runs the same queue by hand: it merges current `main` into the pull request and pushes before marking it ready, one pull request at a time; when `main` has not moved since its last full run, that run stands. A pull request already ready when `main` moves goes back to draft first, or auto-merge stays off on that repo. A clean merge of current `main` keeps the review, unless `main` changed a file, interface or schema the audit named or the change calls: then the reviewer reads that part again. A merge that needed conflicts resolved, or a hand edit, in any file but `progress.md` makes it stale; so does any other commit that changes more than `progress.md`. Branch protection does not require branches to be up to date, so a waiting pull request is never updated just because `main` moved. The pull request records three commits: the one reviewed, the integration commit tested (its head merged with current `main`), and the `main` commit it was tested with. The session that merges watches `main` after the merge. It reads the gate's summary of `main`'s run ("Tests that passed only on a retry"), records each listed test under "Flaky tests" in `docs/superpowers/progress.md` in its next pull request, and reports them to the coordinator. If a post-merge check fails, it reports at once and owns the failure, with a revert if the merge caused it, until `main` is green or the owner takes it over.
- A required check that is red on `main` as well is an existing failure, not this pull request's: report it and give it its own thread. The pull request keeps going and merges once that thread fixes `main`, unless the owner authorizes an exception for that check, named in the pull request. A check that is not required never blocks a merge.
- Extra checks for lane 2: the full run, not the quick one; a fresh review session on what the change touches (see `review`); and a clean run: unchanged code is never retried into green (a rerun that validates an actual fix is fine).
- The session that made the change opens the pull request and merges it once its lane allows: lane 1 on green, lane 2 after its review, lane 3 on the owner's word or a standing permission that covers it. It is a merge commit, never a squash, then the branch is deleted, and a pull request whose lane has opened and whose checks pass is never left open. Where the repo allows auto-merge, it queues the merge (`gh pr merge <number> --auto --merge`) in the step that marks the pull request ready, at its turn in the queue; if `main` moves first, it turns it off (`--disable-auto`) and goes back to draft. It still watches the run and `main` after the merge.
- A tool that appends its own footer to a pull request body (a "Generated by" line) breaks the identity rule in CLAUDE.md. Write the correct body to a file, have a session whose tools add none apply it, or on a public repo give the owner the command (`gh pr edit <number> --body-file <file>`), and check the last line again.
- On a private repo, a merge, or any lane 3 step, run by a session on the owner's computer in an automatic permission mode needs the owner's own typed words in that session: a decision-card tap or a request from another session does not count.
- The implementer owns a required check that fails because of the change: that failure is the implementer's to diagnose, fix and rerun. Report a material effect on outcome, timing or confidence through the owner updates. Pause for an owner decision only when blocked by a decision, access or budget.
- The session that merges reports each merge. It stops and reports to the coordinator, instead of resolving it, on: a merge conflict it cannot resolve cleanly, a golden that moved without a commit naming it, more branches than the limit, a pushed branch nobody asked it to merge, or a lane 3 item no standing permission covers.
- When a pull request merges, mark its outcome complete in the active milestone in `progress.md`. When that milestone closes, archive its record in `progress.md`'s History section. Add a lesson line only if the work taught a lesson no test can catch (see `review`). The active coordinator owns this; otherwise the implementer does.

## The finished result

The owner approves this once, when the whole piece of work is done (a finished spec, or a game milestone), not at each merge. Report how it went, measured: elapsed delivery time (from the brief's approval, which on the short path is the request, to the last merge), time spent waiting (on CI, on the owner), owner interventions, rework (fix rounds and reverts) and escaped defects (failures found after a merge). Line counts, test counts, sizes and ticked percentages are supporting information only. Say what ran, what did not run and why, and give a preview link when the repo has one. Summarize material decisions made during the work, their reasons and remaining limitations. Interim updates and previews follow "Owner visibility and early steering"; significant surprises must not first appear in this final report.
