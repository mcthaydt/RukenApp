## Found while planning

1. **`workers.dev` is a public suffix, so the test site and the gate are the same site** (read in the public suffix list, 2026-11-15: `workers.dev` is listed; so `ACCOUNT.workers.dev` is the registrable name, and `ruken.ACCOUNT.workers.dev` and `ruken-games.ACCOUNT.workers.dev` are two origins of one site). The rebuild plan says they are "a different site"; that is not so. What still holds: the site's cookies have no `Domain` and are host-only (`src/features/accounts/cookies.ts`), so a game cannot read or set them, and a game's script cannot read anything from the site (another origin, no CORS). What does not hold until the games domain exists: `SameSite` no longer keeps the site's cookies off a request a game makes to the site. What stops such a request today: the gate's `connect-src` (no `fetch`, socket or beacon to the site), the frame's sandbox (no form, no popup, no navigating Ruken's page), SvelteKit's origin check on form posts, and that the site has no `GET` that changes anything without a sealed state (read 2026-11-15: `api/auth`, `make/github`, `make/github/callback`, `healthz`). So until launch only games the Owner trusts are accepted on the test site (Task 24 says so), and Task 32 pins the cookie rule with a journey.
   One more thing does not hold (found in the plan audit): a game can **set** a cookie on the whole of `ACCOUNT.workers.dev` (its frame has `allow-same-origin`, and a same-site frame's cookies are not blocked), and the site then receives it. The site's sign-in cookies are `__Host-` cookies on https (`cookies.ts`, `auth.ts`), which no other host can set or overwrite, so a game cannot sign a person in or out. `rk_arrival` and `rk_welcome_back` have plain names, so a game could put a sealed arrival it got from its own link in front of the person's own (credit for a new member, design 6), or fill the cookie header until the site refuses that browser. On the test site, with Stripe's test mode and trusted games, this changes nothing; the games domain at launch removes it, and launch's list below carries it.
2. **Two journeys in the slice 2 plan could not pass on branch S.** Task 30's "it is live at its address" and Task 31's "a member's game stops loading" open `/g/<game>` and `/g/<game>/play`, which arrive with branch F, after S. 3. **A game written straight into the database has no files in the bucket.** M's `fillAnswers` and `putGameWhereStaffLeaveIt` write rows only. - Produces:
  - `checkAddressPattern(pattern: string): void` also accepts the path form: `https://<host>[:port]/{name}`, with `{name}` as the whole of the one path part and nothing after it. `http` only for `localhost` and names under it, as today. The refusal's words name both forms: "GAME_ADDRESS_PATTERN must be one address, like https://{name}.example.com or https://games.example.com/{name}: {name} once, as the first part of the name or as the whole path."
  - `gameAddress(pattern, name)` is unchanged: `https://h/{name}` and `g-abc` give `https://h/g-abc`. So `sessions.ts` (the frame's address) and M's `media(key)` work with either form and are not touched.
  - `GateDeps` gains `pathHost?: string`: the one host (as `URL.host` writes it: lower case, with its port when it has one) on which path mode answers. Unset: no path mode anywhere.
  - On `pathHost`: `/media/<key>` is a clip or a photo, as `media.<domain>/<key>` is; `/g-<id>/<pass>/<path>` is that game's file, as `g-<id>.<domain>/<pass>/<path>` is; `/g-<id>/<pass>` is sent on to `/g-<id>/<pass>/`; anything else is "Not found.". The health check and `robots.txt` answer as on any name.
  - The gate Worker reads `PATH_HOST` (optional), trimmed and in lower case, so a value pasted with a space or a capital still matches `URL.host`. Unset or empty, `pathHost` is not passed.
  - On the one free address every game shares one origin, so `connect-src 'self'` and `cross-origin-resource-policy: same-origin` reach every game's folder there. Nothing changes for that: a file still needs a pass made for its own game, and the Owner chose one shared address until launch.

Approach: `serveMedia` takes the key and `serveGameFile` takes the path after the game and the prefix its redirect needs (`""` or `/g-<id>`), so both modes run the same two functions and every header is the same.
