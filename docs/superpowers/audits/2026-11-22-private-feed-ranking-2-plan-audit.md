## Red findings

**R12.** UNIT: section 3 "Where it runs" and P4 (the production environment). VERDICT: red. REQUIREMENT: section 1 (the app works the same when the private Worker is missing) and C9 (the live site serves the first page); the deploy must not break production. REASON: in Wrangler, bindings are not inherited by an environment, so an `env.production` that adds only `services` (and "every production-only setting") deploys a `ruken` without its database and file bindings. EVIDENCE: `wrangler.jsonc` today holds `hyperdrive` (`HYPERDRIVE`) and `r2_buckets` (`GAME_FILES`) at the top level, both used in production and in `wrangler dev`; Cloudflare's Wrangler configuration documents `hyperdrive`, `r2_buckets`, `services` and `vars` as non-inheritable keys that must be repeated in each environment. The spec says P4 "moves every production-only setting into that environment", which does not move these shared ones. The deploy is `wrangler deploy cloudflare/worker.js` (`package.json:16`), so nothing fails before the live site loses its database. EXPECTED: `env.production` repeats every non-inheritable key the top level has (today `hyperdrive` and `r2_buckets`, plus any `vars`), and a check proves it before the first deploy with the new config. FIX: in section 3 and P4, add "repeats every non-inheritable key of the top level (today `hyperdrive`, `r2_buckets`)"; add to C9 (or a new C16): "`wrangler deploy --dry-run --env production` (or with the deploy-only config) lists `HYPERDRIVE`, `GAME_FILES`, `ASSETS` and `PRIVATE`, shown in P4's pull request". The `wrangler.deploy.jsonc` route needs the same check. Files: the spec only.
