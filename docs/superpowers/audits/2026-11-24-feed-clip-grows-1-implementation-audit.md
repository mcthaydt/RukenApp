# Feed clip grows into the game page: implementation audit 1 (PR #393, lane 2)

Commit examined: 21b47c6f67412e03a5fe916421b2f177633d19c9 (base main d5988b3; it also merges cleanly with main eaaf8a7). Reviewed 2026-11-24 14:59 UTC.

**Verdict: 21b47c6 FAIL, 2 red, 3 notes.**

## What holds

- **The video really moves, and it is not a cross-fade.** A probe read the keyframes the browser built at `ready`. Feed to game, phone WebKit: `::view-transition-group(clip)` goes from 375×667 at (0,0) to 351×413.5 at (12,12). Computer Chromium: from 1280×720 at (0,0) to 622×617 at (12,12). `::view-transition-old(clip)` runs `clip-hands-over` (opaque until 80%, then gone), `::view-transition-new(clip)` has no animation, and the root fades underneath. So the picture that was pressed is the thing that travels.
- **The name does not leak.** At `ready` only one element carries the name `clip` (`DIV:clip` going on, `VIDEO:clip` coming back), and after each move none is left. The journey's `namedLeft` checks this too. The feed only tags the clip on screen (`index === current`), so a game that shows twice in the endless feed is still tagged once.
- **Reduced motion** goes through the layout's existing early return, which starts no view transition and sets no name. The new journey and `page-moves.test.ts` "with less motion asked for" both pass on phone WebKit.
- **Fallback.** Without `startViewTransition` the layout returns before `grownGame`/`slideWhile` run, so no name is ever set. Checked by reading only: all three test profiles have view transitions, so no journey runs this path.
- **Play from the feed** still slides ("on", no clip group). That is the journey's second test, and it passes.
- **Runs.** Phone WebKit in `mcr.microsoft.com/playwright:v1.63.0-noble`: page-moves, game-page and feed all pass, except R1 below. PR CI: the quick draft run is green (verify, postgres, shards 1 to 6, gate). The full run has not started yet.

## Red

**R1.** UNIT: `src/features/feed/Feed.svelte` (`data-grows={index === current ? …}`) with `src/lib/page-moves.ts` (`clipOf` in the update callback). VERDICT: red. REQUIREMENT: the brief says "Back reverses the move". Repo rule: a test that fails once and passes on retry is a defect. REASON: on Back, the feed comes back with `current = 0`, and `current` only reaches the left clip later, once the IntersectionObserver reports it. When the update callback runs `clipOf(game)` before that, it finds no element, so the clip never shrinks into the feed. The page only fades. EVIDENCE: `tests/browser/feed-to-game-grow.test.ts:101` failed 3 times in 11 runs on phone WebKit (1 of 1, 1 of 4 with `--repeat-each=4`, 1 of 6 with `--repeat-each=6`). It received `["clip moved", "played"]`. EXPECTED: Back from a game opened in the feed shrinks the clip every time, and the journey passes 10 runs out of 10. FIX: make the feed's returning clip carry `data-grows` from its first render on Back. For example, the feed keeps the slug and index it was left at and starts `current` there, or `clipOf` waits until the feed has placed itself before naming. Files: `src/features/feed/Feed.svelte`, `src/lib/page-moves.ts`, `src/routes/+layout.svelte`, and the journey (to check it with `--repeat-each`).

**R2.** UNIT: `src/routes/+layout.svelte` (`grows = game !== null && clipOf(game) !== null`). VERDICT: red. REQUIREMENT: the shared name is for the feed to game move only; every other move keeps its slide (owner, 2026-11-22: moves slide like an app). REASON: on any move from a game page to `/`, the page being left always has the clip box. So moves that never came from the feed's clip become "grow": opening a game from a link or a maker's page and pressing Home, or Back to a feed whose clip on screen is another game. These moves lose their "back" slide. The game's clip box then stays stuck on top of the fading feed for 240 ms and disappears, with no partner to move into. EVIDENCE: a probe on computer Chromium opened `/g/<slug>` directly and pressed Home. The result was `data-move="grow"`, the feed's current clip was a different game, there was no `::view-transition-group(clip)` animation, and only `::view-transition-old(clip)` ran `clip-hands-over`. Before this change, `moveBetween("/g/x", "/")` gives "back". EXPECTED: a move from a game page to the feed grows only when the feed will show that game's clip (in practice, Back to the feed the game was opened from). Otherwise it slides "back" as before. FIX: grow on game to feed only for a Back whose earlier move grew from the feed, or name the old clip only once the new page's partner is known to exist. Add a journey for opening a game page directly and pressing Home, expecting `data-move="back"` and no clip group. Files: `src/routes/+layout.svelte`, `src/lib/page-moves.ts`, `tests/browser/feed-to-game-grow.test.ts`.

## Notes (not blocking)

- N1. The no-view-transitions fallback has no journey, since every profile supports view transitions. A Vitest check of the layout's early return, or a journey that deletes `document.startViewTransition` in an init script, would hold it.
- N2. `slideWhile` clears names in `slide.finished`. When a later move skips this one (Back pressed mid-move), that cleanup can run after the later move has already set the same element's name as its old picture, and remove it before the browser takes the picture. The later move then only fades. Found by reading, not probed. It is a small degradation, not a leak.
- N3. `look.css` gives every `[data-move]` root `mix-blend-mode: normal`. The probe shows the UA's `-ua-mix-blend-mode-plus-lighter` animation still runs on the root under "grow", so the cross-fade does not dim. No change needed. It is written down here so the next reviewer doesn't have to check it again.
