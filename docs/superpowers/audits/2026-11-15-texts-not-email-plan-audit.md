## What holds

- **Scope.** The plan builds only what the approved spec asks. No new package: the `phoneNumber` plugin is in better-auth 1.7.7 itself (read in the package). It waits for its place in the slice order, as the plan says.
- **The plugin does what the plan says.** Read in `routes.mjs`: `/phone-number/verify` signs in whoever holds a right code, and makes an account when `signUpOnVerification` is set and none has the number. `/phone-number/request-password-reset` stores a code whatever the number and texts only a real account, so it answers the same either way. `/phone-number/reset-password` calls `onPasswordReset` and then signs every device out. `updatePhoneNumber` refuses a number another account has. `INVALID_OTP` and `TOO_MANY_ATTEMPTS` are its error codes, and three tries are its default.
- **The rate limits apply as written.** Read in `rate-limiter/index.mjs`: the plugin brings its own rule (10 a minute for every `/phone-number` path), and `customRules` named by exact path replace it. Every path the plan names is named exactly.
- **The words fit.** Measured with the three site addresses Ruken has or will have (`https://ruken.io`, `https://test.ruken.io` and a `workers.dev` address of 34 characters): the longest fixed text is `signInPausedText`, at 149 characters with the `workers.dev` address. Every text starts "Ruken:" and holds one link at most.
- **The two numbers.** Twilio's error page for 21610 says a person opts out of "your Twilio phone number, Channels sender, or Messaging Service". That fits one service's STOP leaving the other's texts flowing, but it does not prove it. Task 0 still proves it with a real phone, as planned.
- **The other plans' rewritten sections** agree with this plan's names (`tellByText`, `tellByNews`, `fitText`, `sendPaper`, `TextSent`, `WaitingNotice`, `TEXT_ACCOUNT_NUMBER`), and each says which of this plan's branches must be on `main` first. Beta builds' testers by @name only, slice 4's five maker texts and the wishlist's launch text all match the spec's table.
- **Drunk grandma.** Each screen has one blue forward button, and Back, Keep and "Text it again" are green. Nothing is red, and nothing here can't be undone. Every error has its own plain line.

## Findings that would have stopped or broken the build

1. **Task 7, Step 0 already has its answer, and it is the stop.** In SvelteKit 3.0.0, `is_csrf_forbidden` refuses any form post whose `Origin` is not the site's, and it refuses one with no `Origin` at all even when `csrf.trustedOrigins` is set (`!request_origin || …`). Twilio's posts come from a server and carry no `Origin`. The check runs at the top of `internal_respond`, before the `handle` hook, so no route or hook can let one post through. The only setting left would turn the check off for the whole site. **Fixed:** `cloudflare/worker.js` (which the journeys also run, through `wrangler dev`) gives a `POST` to `/webhooks/twilio` the content type `application/vnd.ruken.twilio-form` before the site sees it. The route reads the body as form fields whatever its type. The signature covers the fields, not the content type, so the check is as strong as before. Step 0 now confirms that Twilio sends no `Origin`, rather than looking for an exemption.
2. **"A throw answers 500 so Twilio sends it again" is not true by default.** Twilio's "Webhook connection overrides" page: by default Twilio retries once, and only when it cannot connect (`rp` default `ct`, `rc` default 1). A STOP that hit a 500 would be lost. **Fixed:** both webhook addresses (the services' incoming address in X3, and `statusCallback`) end `#rc=3&rp=5xx,ct,rt`. Step 0 reads whether Twilio's signature covers the part after `#`, and the stand-in signs the same way. Finding 3 also makes a lost STOP heal itself.
3. **A send that Twilio refuses with 21610 loses the notice.** Twilio answers 21610 when the person has opted out. Ruken only learns of a STOP from the webhook. If that post was lost or has not arrived yet, `tellByText` throws, rolls back and rethrows, and the notice is gone. The spec says every such notice waits on `/me`. **Fixed:** in `tellByText` and `tellByNews`, a `TextError` with Twilio's code 21610 records the stop (`recordStop`, `providerId` `refused:<TextSent key>`) and answers as a stopped line: `waiting` with a `WaitingNotice` for an account text, `stopped` for a news text. A code refused with 21610 records the stop too, so the next screen shows the START words. A STOP and a START that both go missing still leave Ruken wrong until the next send; that is said in the plan.
4. **The purge would leave STOP records behind.** Task 7 says the purge deletes a person's `TextStopEvent` rows, but `deletion.ts` is not in its files and no test checks it. The rows hold a hash of the number, not the person's id, so the purge must make the hash before it clears the number. **Fixed:** Task 7 modifies `deletion.ts` and its Step 1 has the case.
5. **`hasMoney` could not be handed in as written.** better-auth's `sendPasswordResetOTP` is built once, inside `createAuthServices` in `accounts`. `accounts` may not import `membership` or `money` (the layer rule), and "`services.ts`' caller" is `authServices()`, which is in `accounts` itself. **Fixed:** `accounts.ts` exports `setMoneyCheck(check)`, which `src/hooks.server.ts` calls at start with the membership and money reads, as it already does with `setFileStore`. Until it is set, the check answers true, so a reset never goes by text on a guess.

## Security and privacy

6. **The sign-up form could tell a stranger which numbers have accounts.** For a new number `startSignUp` calls `/phone-number/send-otp`, which counts against better-auth's per-client limit (5 an hour) and the per-number limits, and writes a `Verification` row. For a number with an account it sends `alreadyText` and calls none of those. The sixth try in an hour would answer "too many" only for numbers with no account, and the extra database write makes the two answers take different times. **Fixed:** both paths call `send-otp`. The plugin's `sendOTP` callback looks the number up and, when an account has it, sends `alreadyText` in place of the code. The limits, the stored row and the timing are then the same. The stored code is never usable, because `finishSignUp` refuses `verify` when an account has the number. Task 8's taken-number case works the same way.
7. **Codes are stored readable.** The plugin stores each code as plain text in `Verification.value` (`${code}:0`). Today a reset link's token is stored only as its hash (`auth.ts`: "a copy of the database holds nothing that can reset a password"). The plugin has no option to hash its codes. A code lasts ten minutes and allows three tries, so this is a small risk. **Fixed** by saying it: it is now one of the Calls and is under "Worth the Owner's eye". The `storeIdentifier` override for `reset-password:` is no longer used by anything, so Task 4 removes it.
8. **Changing the number needed only a signed-in session.** Someone with a stolen session could change the number, then reset the password, and the account would be theirs. The old number gets one text and has no way to undo it. **Fixed:** `/me/number` asks for the current password first, checked against the account's hash with better-auth's own hasher. A wrong one reads `wrongPassword`. The spec says nothing either way; this adds one field to a screen the spec already has.
9. **A stranger who knows a number can lock its owner out for an hour, again and again.** The plan counts some limits per number only: 1 code a number every 30 seconds, 10 an hour, and ten wrong codes pausing codes for an hour. Ten wrong codes need only four requested codes, about two minutes. With the sign-in pause also reached by ten wrong passwords, the person has no way in. Slice 1 kept per-client counts on purpose to stop this (the comment in `auth-limits-plugin.ts`). The ten-wrong-codes pause is the approved spec ("Ten wrong codes pause codes for that number for an hour"), so it is not reopened, and the plan keeps it. Said once, with these facts, under "Worth the Owner's eye". **Held by the Owner** if they want it changed.
10. **Texts to every country invite fraud.** A public form that texts any number in 222 countries is a known target: people sign up premium-rate numbers and keep part of what Ruken pays. Twilio's "SMS Geo Permissions" page says a new account can text only its home country, and Twilio advises leaving off the countries a business does not use. **Fixed:** X2 turns on Canada's permission, X7 turns on each country's permission when it opens, and Task 11 says `open` in `countries.json` and Twilio's permission must match. Step 0 of Task 1 also reads Twilio's page on SMS pumping protection, and reports whether it applies to Messaging Services.

## Spec and correctness

11. **Outside the US and Canada, nobody can text Ruken back, even in the 43 "two-way" countries.** The country table says replying "needs a number of that country". Ruken will have two US numbers. So a person in the UK or Australia cannot reply STOP or HELP either, and Task 11 would show them "Reply STOP to stop", which would not be true. **Fixed:** the words depend on a new field, `replyHere` ("Ruken has a number in that country on that line"), not on `twoWay`. At first it is true only for the US and Canada. Canada shares the US numbering plan, so a Canadian phone should be able to text a US number, but no page or test proves it yet; Task 0 records it as unproven unless a Canadian phone is at hand. **For the open question (Question 1):** its card says "most of the world outside the 43". With two US numbers it is really every country except the US and Canada, until option B buys numbers. The coordinator is told, so the card can say it right. This audit does not answer the question.
12. **Opening a country is more than one line.** A country accepts only some kinds of sender (the table's last three columns). A US number cannot text Austria, for one ("Number from abroad: Not Supported"). So each country also needs a sender that it accepts, in both Messaging Services: the name "Ruken" (registered where required) or a local number. That is the Owner's step and may cost money. **Fixed:** `countries.json` records the `sender` each country needs, X7 says to add it to both services, and "opened by one line" now says "after X7".
13. **"160 characters" is not one text.** One character outside the basic text alphabet (GSM-7) switches the whole text to a wider encoding, where one part holds 70 characters. That could be a curly apostrophe, an emoji, or most non-Latin letters in a game's name. A 160-character text then goes as three paid parts. Some ordinary characters (`€ [ ] { } | ^ ~ \`) take two places. **Fixed:** `fitText` and every words test count GSM-7 places (at most 160). When a name needs the wider encoding, `fitText` cuts the whole text to 70. The fixed words use straight apostrophes only, and a test checks that each is plain GSM-7.
14. **Sign-in could not find a number typed for another country.** Sign-in had one phone field, read as the country the browser suggests. Review Focus 1's own case, a UK number with the country left on +1, became `+17700900123`, which reads as a wrong password every time. `toE164` also missed "1 312 555 0142" typed with +1 (`+113125550142`, 12 digits, which passes the 8-to-15 rule) and numbers typed with `00` or `011` in front. **Fixed:** sign-in has the same Country list as sign-up, and `toE164` drops a leading `1` under +1 and reads `00` and `011` as `+`, with test rows for each.
15. **A failed sign-up could leave an adult treated as a child.** `verify` makes the account and signs the person in before the transaction that writes the password and `adultOn`. If that transaction fails, the account has no password and no `adultOn`, and null means "every under-18 default applies", with no screen to fix it. A second try then meets "an account has this number" and fails too. **Fixed:** when the transaction fails, `finishSignUp` removes the half-made account (its `User` and the new `Session` row, in one more transaction). It keeps the pending row, signs the person out and shows "Something went wrong. Try again." with "Text it again".
16. **The news yes could not stay one fixed sentence.** `NEWS_YES_WORDS` is a constant, but Task 11 changes its ending by country. **Fixed:** `newsYesWords(country)`, and the record keeps exactly the words shown.
17. **A text with no device time zone could wake Hawaii.** With no zone from the device, Task 9 used the country's main zone, which for the US is Chicago until Task 11, and the capital's zone after it. 9:00 in Chicago is 5:00 in Hawaii. The spec names "an optional text that wakes someone at night" as a failure. **Fixed:** with no device zone, a news text goes only when it is between 9:00 and 20:00 in every zone of the number's country. `countries.json` holds `timeZones`, not one main zone.
18. **The stand-in's two addresses were read from one setting without saying so.** `TwilioTexterOptions` has `apiBase` and `lookupBase`, but `services.ts` reads only `TWILIO_API_BASE`. **Fixed:** both come from it, since the stand-in serves both.
19. **An Apple member buying an extra on the web had no address for legal papers.** Only the membership checkout calls `setPaperEmail`. A member who joined through Apple never went through it, so the sales plan's EU and UK confirming email would hit `no_address` and be thrown to "Needs a person" every time. **Fixed** in the sales plan's rewritten Task 14: the extras checkout's handler also calls `setPaperEmail`.
20. **The HELP reply points at a page that may not exist.** `helpText` sends people to `<site>/help`. The help chat is not approved, and the legal pages are held on #104. The carriers read the HELP reply when they review Ruken's number. **Fixed:** X5 now waits for `/help` to be public too, beside the privacy and terms pages.
21. **The US and Canada split needs a source.** `countryOf` tells the two apart by area code, but the plan does not say where the list of Canadian area codes comes from. **Fixed:** Task 11's Step 0 takes it from the numbering plan administrator's published list, and `README.md` records it.
22. **One row of the country table is broken.** The row `BN | BN | ?` lost its name (Brunei) and its dialing code when the script read the page. Task 11 reads every page again, so nothing is built from it. It is noted here only.
