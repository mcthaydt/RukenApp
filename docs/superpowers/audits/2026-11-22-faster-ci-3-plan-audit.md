## Red

**R1.** UNIT: spec 3.4 item 1. VERDICT: red. REQUIREMENT: the spec must let the builder get the cache version right, which is the very failure F exists to fix. A plan must also make a missed restore visible (release, "a check is a test that fails by itself"). REASON: the version includes the `path` string, but 3.4 names keys and never paths. It also never says what `test-times` does when one of the six exact restores misses. EVIDENCE: 3.4 item 1 says "saves its own times under `ci-piece-times-<sha>-<n>`" and "restores the six by exact key", with no path. Say a piece saves `path: piece-times.json` and `test-times` restores into `path: pieces/piece-times-1.json`, or any other string. Every restore then misses with only a log line and `cache-hit` empty. `test-times` would then save a file with some or no pairs, and the planner would quietly fall back to the median for them. F1 would catch none of this, because pieces would still "Split by main's recorded times". EXPECTED: the spec names the exact `path` each piece saves (for example `piece-times-${{ matrix.shard }}.json`, which evaluates to one literal per piece) and the identical literal each of `test-times`' six restore steps uses. It also names `ci-test-times.json` as the one path for the joined save and every piece's restore. It says `test-times` restores with `fail-on-cache-miss: true`, so a missing piece fails that job (nothing waits on it) instead of saving partial times. It adds an acceptance line: on the first `main` run after F, `test-times` restores six of six and logs the number of pairs it joined, 159 at 7b34a98 (53 files × 3 devices). FIX: spec text in 3.4 item 1 and F1/F2 only. File: `docs/superpowers/specs/2026-11-22-faster-ci-design.md`.

**R2.** UNIT: spec 3.4 item 2, the prefix fallback. VERDICT: red. REQUIREMENT: CLAUDE.md Verification says "A test that fails once and passes on retry is a defect: record it under 'Flaky tests'". `gate` is the one required check. REASON: the spec accepts a race that makes `gate` fail once and pass on retry. It gives no bound on how often that happens, and no way to tell it from a real lost journey. EVIDENCE: the race needs `ci-test-times-<base>` to be missing when some pieces restore and present when later ones restore, so the window is the spread between the pieces' restores. In run 44989252655, "Fetch main's test times" started at 05:25:52 (piece 1), 05:28:13 (6), 05:30:10 (5), 05:30:16 (4), 05:30:46 (3) and 05:31:06 (2): a spread of 5 min 14 s, from runner queueing. A `main` run takes about 14 min (44989107147: 05:22:10 to 05:36:18), and merges come minutes apart (05:52:04, then 05:58:49). Take a pull request updated just after a merge, or the next merge's own run on `main` (`github.event.before`). Its base's times can land inside that window: the early pieces deal from the older file and the later ones from the base's file. The union check then reports missing and doubled pairs, exactly as for a lost journey. A re-run of `gate` alone re-reads the same artifacts and fails again, while a full re-run passes. On `main` this turns `main` red. EXPECTED: the spec does one of two things. (a) It removes the race. Any lookup whose answer can change while the pieces start still races, and that includes falling back to `--shard` on a miss. So in practice this means a small planning job that restores once and hands every piece the same file. That job adds a `needs`, which A1 forbids today, so choosing it changes A1. (b) It keeps the race but bounds and names it: each piece adds its `cache-matched-key` to its `ran-*` artifact. `gate` compares the six keys first and, when they differ, fails with "the pieces read different times (keys …); re-run all jobs" instead of a missing/doubled list. The spec states how such a run is handled under the flaky-tests rule, and F1's measuring counts how often it happens. FIX: spec text in 3.4 item 2 and F1/F2, plus A1 if (a). File: `docs/superpowers/specs/2026-11-22-faster-ci-design.md`. Which option to take is a process choice for the coordinator, not the owner's, since both stay within the budget.

## Notes (not blocking)

- **N1. Old zstd entries.** The `ci-test-times-*` entries saved on the host stay in the cache until they are evicted. Lookups from inside the image never see them, so they are harmless, and evicting them needs no step. The spec could say so in one line, so nobody spends time on them.
- **N2. Eviction.** The repository's pnpm caches are about 180 MB each (piece 1's log: "Cache Size: ~180 MB"), against GitHub's 10 GB per repository, evicted oldest-used first. If the times entries are ever evicted, pieces fall back by prefix or to `--shard`, so no journey is lost. Not a defect.
- **N3. Re-runs.** A re-run of a `main` run saves under keys that already exist. `actions/cache/save` then warns that it cannot reserve the key, and the job does not fail. So "re-run failed jobs" after a piece failed gives `test-times` all six. The spec can rely on this.
