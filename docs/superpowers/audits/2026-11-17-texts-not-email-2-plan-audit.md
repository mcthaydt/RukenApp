## Red findings

**1. A second sign-up for the same number can set the password on someone else's new account.**
UNIT: Task 4, `pending-sign-up.ts` and `finishSignUp`. VERDICT: red. REQUIREMENT: Review Focus 2's spirit and the Call "A code never signs anyone in to an account that exists"; B2. REASON: the pending row is keyed by the number alone and "a newer try for the same number replaces the row", and `finishSignUp` takes whatever row is there. EVIDENCE: Pat starts sign-up with their own number and gets a code. Before Pat types it, a stranger who knows the number starts sign-up with it and their own password (allowed after 30 seconds); the row now holds the stranger's hash, and Pat gets a second code. Pat types a code: `verify` makes the account, and the credential row gets the stranger's hash. The stranger signs in with Pat's number and their own password; Pat's password fails. EXPECTED: a code typed in one browser finishes only that browser's sign-up. FIX: bind the pending row to the browser that started it: a random value in a short-lived `httpOnly` cookie, its hash stored with the row (`@@id([numberHash, browserHash])` or a column checked by `takePending`), so a later try from elsewhere adds its own row and replaces none. Add a journey: two browsers, one number, the second starts after the first; the first finishes, its password signs in and the second's does not. Files: Task 4's `pending-sign-up.ts`, `forms.ts`, Task 3's `PendingSignUp`, and their tests.

**2. At the wrong-code limit, sign-up tells a stranger which numbers have accounts.**
UNIT: Task 4, `finishSignUp` and the wrong-code hooks. VERDICT: red. REQUIREMENT: B2 ("no code typed there signs anyone in, even at the limit"), Global Constraints ("the same screen, the same words and the same timing either way"), audit 6. REASON: for a number with an account `finishSignUp` answers `codeWrong` without calling `verify`, and the wrong-code counter is an `after` hook on `/phone-number/verify`, so those tries are never counted. EVIDENCE: eleven wrong codes for a number with no account read "Too many wrong codes. Codes are paused…"; for a number with an account they keep reading "That code isn't right", and the next code request still goes through. Skipping `verify` also skips its database work, a timing difference. EXPECTED: both cases read the same at every try. FIX: in the existing-account branch, check the code through the plugin's server-only `auth.api.consumePhoneNumberOTP` (in 1.7.7, no route, never public; it checks and uses up a code without making a user or a session), count `INVALID_OTP` and `TOO_MANY_ATTEMPTS` under the same `api:auth:wrong-code:<hash>` key, refuse with `CODES_PAUSED` the same way, and answer `codeWrong` whatever the result. Add a case to the "even at the limit" journey for codes typed, not only codes asked for. Files: Task 4's `forms.ts`, `auth-limits-plugin.ts`, their tests.

## If the Owner picks Twilio Verify for codes

The Owner is being asked whether codes should go through Twilio Verify, which sends from senders Twilio has already registered, instead of the plan's own Messaging Service, which US carriers block until X5. This does not rewrite the plan. It lists what in A and B would change. Twilio's pages were not read in this session (only titles: "Customization Options", "Verifications", and error 60204 "Service does not support this feature"); the plan session reads them before changing the plan.

**What gets better.** A real code can reach a US phone before X5, so the slice's last step can pass and B can merge without waiting on the carriers ("Open before the build" goes away for codes). Codes are no longer kept readable in Ruken's database for sign-up (audit 7). Twilio's own fraud guard covers code texts.

**What changes in branch A**
- `Texter` gains two calls, for example `startCode(number)` (POST `…/v2/Services/{VA…}/Verifications`, `To`, `Channel=sms`) and `checkCode(number, code): "right" | "wrong" | "expired"` (POST `…/VerificationCheck`). The made-up-number and allowlist guards apply to `startCode` too. One new setting, `TWILIO_VERIFY_SERVICE`.
- The stand-in serves both Verify addresses, keeps the code it "sent", and `textTo` and `codeIn` read Verify's words.
- `codeText` and `resetCodeText` are no longer Ruken's words: Verify sends its own template (custom words need Twilio's approval), so they may not start "Ruken:" or say "Don't share it". A4's tests on them change or go.

**What changes in branch B**
- Sign-up: better-auth 1.7.7's `phoneNumber` plugin has a `verifyOTP` option (read in `routes.mjs`): `/phone-number/verify` and `consumePhoneNumberOTP` then ask that function instead of the stored code. `sendOTP` calls `startCode` and ignores the plugin's own code. The wrong-code counter still works, because the plugin throws `INVALID_OTP` when `verifyOTP` answers false.
- **Forgot password does not use `verifyOTP`.** `/phone-number/reset-password` always checks the plugin's own stored code. So either Verify sends that code (Verify's custom-code feature, which Twilio must turn on for the account), or `finishReset` checks the code with Verify and saves the password itself, giving up the plugin's one step (save, `onPasswordReset`, sign every device out) that the plan chose it for. The member's arm, which mails the code, would then need its own code or Verify's email channel. This is the biggest change.
- **`alreadyText` cannot go through Verify**, which only sends codes. Audit 6 (both cases take the same path) would send a Verify code to a number that has an account, which `finishSignUp` already refuses, with no "you already have an account" words. The other choice, a Messaging text, is blocked until X5.
- **`passwordChangedText` and `signInPausedText` are not codes.** They stay on Messaging and still cannot reach a US phone before X5. B4's "the person gets `passwordChangedText`" holds against the stand-in only.
- Limits: Verify has its own attempt and resend limits (its error codes, such as "max send attempts", map to `codeTooSoon` and `codesPaused`); the 30-second rule and the per-number limits stay in front.
- B5 gains a case: Twilio failing on the code check, which runs while the person waits, unlike the send.
- Cost: Verify charges per verification on top of the text.
- X2 gains one command to make the Verify service and X4 one secret. Task 0's Step 1 splits: a Verify code to the Owner's phone can be proved now; the two-number STOP proof still waits for X5.
- Branch C later: a STOP to the account number no longer stops codes (point 2 under "What follows from it"), and Review Focus 3 changes.
