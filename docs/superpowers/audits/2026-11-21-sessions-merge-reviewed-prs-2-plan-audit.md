## Red findings

**R1.** UNIT: spec §3.3 and `main()` in `.claude/hooks/rules.mjs` (lines 1440–1444, 1456–1458). VERDICT: red. REQUIREMENT: §3.3 "The hook must not fail open on these tools"; §1 "Nothing approved this way skips a check". REASON: three exits skip every check with exit 0 and no deny, so neither `onFailure: "block"` nor the planned crash rule catches them: a `rules.json` that is missing or not valid JSON (`if (error) { emit(systemMessage); return; }`), and no root found (`if (!roots.length) return;`). And the crash rule as written ("a crash on one of those three tools answers deny") cannot work when the crash is the input parse, because the tool name is not known yet; criterion 4 even offers that case ("feed malformed input") as its test. EVIDENCE: the broken and missing `rules.json` rows above (a squash merge gets no deny); the `not json` row. A checkout of an older commit or a half-finished edit of `rules.json` is enough. EXPECTED: on a PreToolUse for one of the three tools, any path where the checks did not run ends in a block. FIX (spec, then build in `rules.mjs` only): make every "did not run" path a failure for these tools. The smallest form: on PreToolUse, when the config fails to load or no root is found, exit 1 instead of 0; in the crash handler, exit 1. The second hook entry's `onFailure: "block"` then blocks the three tools, and the first entry (no `onFailure`) keeps today's non-blocking notice for every other tool, so no tool-name test is needed in the handler. Add test cases: broken `rules.json`, missing `rules.json`, malformed input, each giving a non-zero exit; and a settings check that the second entry has `onFailure: "block"` and its matcher.

**R2.** UNIT: spec §3.1, `mcp__github__enable_pr_auto_merge` in the allow list. VERDICT: red. REQUIREMENT: §1 "a lane 2 or 3 pull request is refused without a passing review that names its head commit"; CLAUDE.md "a push that changes what it covered makes it stale". REASON: the hook checks the review only when auto-merge is turned on. A later push by the session keeps auto-merge on, and GitHub merges the new head as soon as the required checks (`gate`, `commit-authors`) pass, with no review on that head. Nothing in the hook looks at `auto_merge` on a push (`grep auto_merge rules.mjs`: only the REST route regexes). The likely path is ordinary: auto-merge queued when marked ready, CI fails, the session pushes a fix. Today the classifier refused the enable, so the owner stood in between; this allow rule removes that. EVIDENCE: GitHub docs quote and repo setting above; `release` line 97 queues auto-merge "in the step that marks the pull request ready". EXPECTED: no unreviewed head of a lane 2 or 3 pull request can merge through a merge the session queued. FIX, one of (spec only now): (a) drop `enable_pr_auto_merge` from the allow list, so it stays with the classifier and the owner as today, and say so; or (b) in `rules.mjs`, refuse a `git push` (and `push_files`-type tools are already refused) to a branch whose open pull request has `auto_merge` set, with "turn auto-merge off first (disable_pr_auto_merge)", plus a test with a stubbed `gh`. (a) is smaller and keeps the brief's scope.

**R3.** UNIT: spec §3.1 "Accepted reach" and `checkMcp` for `update_pull_request`. VERDICT: red. REQUIREMENT: §1 (as R2); round 2 brief, "check what else `update_pull_request` can do once allowed (e.g. retargeting base)". REASON: the spec says a base change "none merges … anything", but it changes what a later merge carries. A PASS names the head commit, and a base change keeps the head, so the PASS still counts while the diff that merges is no longer the diff that was reviewed (a pull request reviewed against branch X, retargeted to `main`, carries X's unreviewed commits). The hook does not look at `base`. EVIDENCE: the `base: "some-branch"` row (no deny); `checkReviewed` compares only `pr.head.sha`. EXPECTED: a reviewed pull request cannot be pointed at different work without a new review, or base changes are not approved by this rule. FIX (spec, then `rules.mjs`): refuse `update_pull_request` with a `base` field on this repo ("the owner changes a pull request's base"); nothing in `release` changes a base. Add a test case. Rewrite the "Accepted reach" paragraph to match.

**R4.** UNIT: spec §1 and §3.1, against `checkReviewed` in `rules.mjs`. VERDICT: red. REQUIREMENT: §1 (as R2); CLAUDE.md Risk, "Classify it from the paths its diff touches … The highest lane wins". REASON: the review gate takes the lane only from the pull request body, and the allowed `update_pull_request` rewrites the body unchecked. A body that names only "Lane 1" (by mistake, or after an edit) merges a lane 3 change with no review, and with this rule nothing stands behind the hook. EVIDENCE: the "Lane 1" rows above: merge and auto-merge get no deny, the "Lane 3" control does; the body edit row: no deny. EXPECTED: a pull request whose changed files are lane 2 or 3 paths needs a passing review whatever its body says. FIX, one of: (a) in `checkReviewed`, also read `repos/<repo>/pulls/<n>/files` and take the highest of the body's lane and the lane its paths give, with the lane 2 and 3 path lists from CLAUDE.md's Risk section put in `rules.json` (`prFlow.lanePaths`), a read failure counting as lane 3; with a stubbed-`gh` test; or (b) the spec states plainly, next to "Accepted reach", that the gate trusts the body's lane, and the owner accepts it as a decision. (a) is what CLAUDE.md asks for; (b) needs the owner.
