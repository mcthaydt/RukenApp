## 1. The outcome

Nobody reading RukenApp can learn how the real feed ranks games (beyond the public "How the feed works" page), how the makers' pool is worked out (beyond the promises in the maker agreement), what the real limit numbers are, or, once built, how fake plays, fake accounts and games are flagged. The public app still builds, tests and runs for anyone, with a simple order of its own. The real order comes from a private Worker built from RukenPrivate, and the app works the same, only in a plainer order, when that Worker is missing, slow or broken.

It has failed, even if every test passes, if: the pool shares money or counts play by any rule but the private one, or differs by a cent from today's on the golden months; a month goes final while the private Worker is not answering; a ranking rule, a weight, a setting value, a signal module, or a hidden layer's code lands in RukenApp after this; the public app cannot be built, tested or run without access to RukenPrivate; the feed errors or stalls when the private Worker is down or comes back; the consent, age and parent's-yes rules move out of public view; "How the feed works" says something the feed no longer does; or the work adds a cost the Owner did not approve.

## 3. The boundary

One interface, in the public repo, `src/features/feed/ranker.ts` (lane 2: shared code), plain data in and out, no private name in it:

```ts
/** Who is asking. Decided in public (consent, age, a parent's yes, the "Learn from what I do" switch). */
type Viewer = { kind: "crowd"; seed: string } | { kind: "full"; seed: string; id: string };

interface RankRequest {
  v: 1;
  viewer: Viewer;
  /** The cursor this ranker made, or null for a first page. Opaque to the app. */
  after: string | null;
  asOf: number;
  /** Everything the ranker may read, as plain rows; the app reads them from the database. */
  facts: FeedFacts;
}

interface RankedPage {
  /** Game ids in order, each with the clip slot to show and a key unique in the feed. */
  items: { gameId: string; slot: number; key: string }[];
  next: string | null;
  caughtUpAt: number | null;
  ask: { index: number; gameId: string } | null;
}

interface Ranker {
  page(request: RankRequest): Promise<RankedPage | "bad-cursor">;
  /** Per game, whether its maker sees "Few people have tapped Play..." (learned spec 6.4, unit F). */
  notes(request: { asOf: number; facts: FeedFacts; gameIds: string[] }): Promise<Record<string, "few-plays" | "few-taps" | null>>;
  health(): Promise<"private" | "partial" | "defaults">;
}
```

- **`FeedFacts`** are rows the app already has or the learned spec's public units add: live games (id, maker, live since, age rating, mood, genre, clip slots), play days (user, game, Chicago day, attentive beats, basis), and, for a `full` viewer, their views, likes, saves, reposts, More/Less rows, Good pick answers and reset time. It grows only by adding optional fields; `v` bumps on any other change. Which rows are read is public on purpose: it is what a person is told is collected.
- **Where it runs.** RukenApp's Worker gets a service binding `PRIVATE` to the private Worker `ruken-private` and calls it over Workers RPC. **The binding exists only in the deploy.** The top-level `wrangler.jsonc`, which `wrangler dev` and the journeys use (`playwright.config.ts:87`), has no `services` entry; the deploy's environment `env.production` in the same file adds it, and the deploy scripts name `--env production`. Wrangler does not pass bindings down to an environment, so `env.production` repeats every key the top level has that an environment does not inherit (today `hyperdrive` and `r2_buckets`, and any `vars`), as well as adding `services`. P4's first step reads the deploy scripts and workflow and moves every production-only setting into that environment. If environments would rename the account's existing `ruken` Worker, it uses a separate `wrangler.deploy.jsonc` named only by the deploy instead, with the same full list of bindings, and says which. Either way C16 proves the bindings before the first deploy. `PRIVATE` is declared optional by hand on the app's `Env` type, since `wrangler types` from the top level does not see it (audit 2, N4). `src/features/feed/services.ts` picks the ranker: the binding when present, otherwise the public ranker. In dev, CI and for contributors the binding is absent, never present but dead.
- **The public ranker** (`src/features/feed/public-ranker.ts`) is today's interim order plus the infinite feed's rounds, moved behind `Ranker` with no behaviour change: the order #329 ships is the order a contributor sees. Its cursor is #329's `day~round~offset~swapped~last`. `notes` answers null for every game; `health` answers `defaults`.
- **Falling back.** A call to `PRIVATE` that throws, takes longer than 800 ms, or answers something that fails the contract's shape check is logged in one line (no viewer, no value) and answered by the public ranker.
- **Cursors name their ranker.** The app wraps every cursor it hands out as `p.<cursor>` (made by the private ranker) or `o.<cursor>` (made by the public, open one), and unwraps it before passing it on. A cursor made by the ranker that is not answering now, in either direction, gives a fresh first page; only a cursor with neither prefix, or one its own ranker answers `bad-cursor` to, is the route's 400. A fresh first page in the middle of a scroll shows round 0 again: that repeat is the accepted way the feed degrades during an outage or on the Worker's return, and nowhere else (audit 1, N5).
- **Settings the public app reads.** Three settings decide what the app itself does, not how games rank, so the app reads them: `learned` and `teenPersonal` (whether a viewer is `full`, and whether a view is stored at all: learned spec 10.2) and `windowDays` (how long watching rows are kept before RukenApp's daily job deletes them: learned spec 3). The app reads them from a Worker secret `FEED_PUBLIC` on `ruken`, a small JSON loaded by the same RukenPrivate workflow that loads `FEED_SETTINGS` on `ruken-private`, from the same file, so the two never disagree. When `FEED_PUBLIC` is missing or bad, each falls to its safe side: `learned` off, `teenPersonal` off, and `windowDays` a short public default. `playwright.config.ts` gives `wrangler dev` a `FEED_PUBLIC` with `learned` on and public placeholder values, as it already gives the other settings (`playwright.config.ts:93-95`), so the journeys for a `full` viewer run as `full` (audit 2, N1). These three names, and only these, may appear in RukenApp (C5). They are switches and a keeping period people are told about, not tuning.
- **"How the feed works" stays true.** That page is where a person is told what the feed does, and it stays public. P2 repoints its source comment (`src/routes/help/how-the-feed-works/+page.svelte:2-6` on its branch, which says it follows `order.ts`) to `public-ranker.ts` and to this rule: a private ranking change that makes the page's words untrue merges only after a RukenApp pull request that changes the page has merged (the reverse of "private half first"). RukenPrivate's pull request template asks "Does the public page still say what this does?", answered in every ranking pull request.
- **What stays public:** the database reads and every migration; the consent gate and who counts as `crowd` or `full` (learned spec 4.1, 10.1), with the three settings above; every screen and route (Your feed, the ••• sheet, Like/Save/Repost, the parent's yes, test videos, the questions for mood and genre); turning ranked ids into `FeedClip`s; `/healthz/feed`, which answers the ranker's `health()`; the "How the feed works" page; `docs/feed-sky.md` in words (section 4).
- **What goes private (RukenPrivate `feed/` and `worker/src/feed/`):** `learnedOrder`, every module under the learned spec's `signals/`, the settings list and its defaults, the cursor format, echo and second try, the slot pick, the few-plays and few-taps rules, the sky sums (`sky.ts`), the high-taste weights, the settings workflow, and the private learned-feed spec itself. The `FEED_SETTINGS` secret is set on `ruken-private`, never on `ruken`; `ruken` gets only `FEED_PUBLIC`.
- **One Worker, one folder per job.** `ruken-private` keeps `src/feed/`, `src/pool/`, `src/trust/` and `src/review/` (section 6), each its own RPC namespace (`feed.page`, `pool.allocate`, ...), its own tests and its own fallback rule on the app's side. A folder is created when its first code lands, not before.

## 8. Risks, and what is not checked

- The rules in words are public for good (section 2); only numbers, code and anything decided from now on are private.
- A slow or failing `ruken-private` gives everyone the plain order. The fallback log line is the only sign; `/healthz/feed` answering `defaults` on the live site is how a check sees it.
- Passing facts per request may outgrow the RPC call as the catalogue grows; C9 measures it, and the learned spec's A10 cache applies on the app's side.
- Two repos must agree on one contract; C7 is the guard. Without its daily run (Open 3), a RukenApp change to `ranker.ts` merges unchecked against the Worker until RukenPrivate's CI next runs.
- RukenPrivate has no browser journeys; the paging invariants are unit tests there, and the journeys in RukenApp run against the public ranker or a stub, never the real one.
- Moving the pool code hides little: the pool's rule and the play count are set by public promises and public play code, and makers lose the ability to rerun their statement's maths from public code (audit 1, N3, said once; the Owner's decision stands).
- A long outage of `ruken-private` holds a month past "final on the 10th, paid on the 15th"; C14's report line is how the Owner hears of it.
