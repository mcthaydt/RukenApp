## 2. The outcome

The pull request rules are enforced on GitHub, where no tool or shell trick reaches: a required check, `pr-rules`, runs on every pull request event and judges the pull request as GitHub has it. Whatever route opened, reopened or edited it, a pull request that breaks a rule fails `pr-rules` (so it cannot merge), and one that takes the open count past 3 is closed with a comment. The client hook stays as the early warning on the routes it can read, plus a narrow allowlist: pull request writes go through plain `gh` or the GitHub MCP tools, nothing else. The CLAUDE.md rule (3.7) is the behavioural backstop.

**Call, after two plan audits (approach reassessed, as the coordinator advised):** two rounds of route-by-route refusals found 9 and then 8 more ways past the hook. A list of command shapes does not converge, because a shell can always build a command the hook cannot read. GitHub sees every pull request, however it was made, so the guard that must hold lives there.

## 3. The change

### 3.1 `pr-rules`, the check on GitHub (the guard)

A workflow `.github/workflows/pr-rules.yml`, whose job is named `pr-rules-run`. It runs only on events that use `main`'s copy of the workflow (audit 3 R1): `pull_request_target` (`opened`, `reopened`, `edited`, `synchronize`, `ready_for_review`, `converted_to_draft`) and `issue_comment` (`created`, `edited`, `deleted`, on pull requests; audit 3 N1). It has no `pull_request` or `pull_request_review` trigger: reviewers post verdicts as comments, which the `review` skill already allows. It checks out `main` only (`actions/checkout` pinned by sha, `ref: main`, `persist-credentials: false`), installs nothing, and runs `node scripts/pr-rules.mjs` with only the pull request number passed in through `env:` (audit 3 R6). Permissions: `contents: read`, `pull-requests: write` (close), `issues: write` (comment), `statuses: write`. Concurrency: one group per pull request (`pr-rules-${{ github.event.pull_request.number || github.event.issue.number }}`), no `cancel-in-progress` (audit 3 N3). The job's condition is exactly `if: github.event.pull_request || github.event.issue.pull_request`, so every `pull_request_target` run goes ahead and an `issue_comment` run goes ahead only when `github.event.issue.pull_request` is set (audit 5 R2), so a comment on a plain issue writes no status and closes nothing (audit 4 R3). Those two expressions and the number under `env:` are the only `github.event` uses.

**The required result is a commit status the script writes (audit 3 R2).** Whatever event started it, the script writes a commit status named `pr-rules` on the head commit it read for that pull request (`success` or `failure`, with the first failing rule as the description), so a comment verdict turns the pull request's check green or red. The job's own name, `pr-rules-run`, never collides with it.

`scripts/pr-rules.mjs` reads the pull request, its files and its comments and reviews through the REST API, and fails (exit 1, with one `::error::` line per rule) when:

1. **Open limit.** More than `maxOpenPrs` (3, read from `.claude/hooks/rules.json`) pull requests from this repo's own branches are open (forks do not count; Owner, 15:00 UTC). A pull request whose `head.repo` is null (its fork was deleted) counts as a fork (audit 4 N1). The count is one function in the shared library, used by the hook too. Every list the guard reads (open pull requests, files, comments, reviews) is read to its last page (audit 5 N1). Ordered by creation time, the pull requests beyond the third are over the limit. On `opened` or `reopened` of an over-limit pull request, the script also closes it, with the comment "Closed: 3 pull requests are already open (#a, #b, #c). Reopen this when one merges or closes." Every pull request counts, docs included (Owner, 3.5).
2. **Lane.** The body names no lane, or names a lane lower than its files' lane (the same `lanePaths` and `lanePathsExcept` from `rules.json` the hook uses).
3. **Acceptance criteria.** The body has no "Acceptance criteria" heading and the files go beyond docs (`ruleMix.docPaths`).
4. **Workflows.** A pull request that changes `.github/workflows/**` fails unless its body names lane 3 (audit 3 R1).
5. **Draft.** A lane 2 or 3 pull request that is not a draft has no passing verdict naming its head commit, counting only comments and reviews written by the owner's account (audit 4 R2; the repo is public, so anyone can comment). The filter lives in the shared `verdicts` function, with the login read from `rules.json` (`prFlow.verdictAuthor`, `mcthaydt`), so the hook's ready and merge checks ignore outsiders too (audit 5 R1), by the verdict format the hook's `verdicts` reads ("<7+ hex> PASS" as the first line of a comment or review, the latest verdict for that commit wins). A clean merge of `main` after the verdict keeps it, as `onlyCleanMerges` does in the hook.

Rule 3 judges "beyond docs" with a docs list that leaves out `.claude/**`, so a hook-only change needs criteria (audit 3 N5). An over-limit pull request left open from before is re-judged on its next event; a `closed` event on another one does not re-judge it, so it stays red until touched, which is safe (audit 3 N2).

The lane, criteria and verdict functions move out of `rules.mjs` into `scripts/pr-rules-lib.mjs`, imported by both the hook and `scripts/pr-rules.mjs`, so the client and GitHub judge by one piece of code.

**Call:** close over-limit pull requests, rather than only failing them. Failing alone stops a merge but leaves the overrun open, which is what the owner objected to. Closing is undone by reopening, and a reopen meets the same check.

**Owner step, one command, after `pr-rules.yml` is on `main`:** add `pr-rules` to the required checks on `main` (with `gate` and `commit-authors`), with no app pin unless criterion 20's measurement shows a `GITHUB_TOKEN` status carries the pinned app id. Sessions' tokens can change branch protection (audit 3 R5), but what is required is the owner's choice, so it stays the owner's command and the hook refuses it for sessions (3.4). Until it runs, the check is reported as "runs but is not required".

### 3.2 The proxy's footer (F4; unchanged since plan audit 2)

**Owner, 2026-11-21 14:43 UTC, on a card:** "Yes, ignore that exact footer".

- The footer is one string in `rules.json`, `prBody.proxyFooter`: the two lines `---` and `_Generated by [Claude Code](https://claude.ai/code)_`.
- `commit-authors` drops trailing blank lines, removes that exact two-line block once if the body ends with it, then judges as today: last line "Requested by **McThayDT**", no other "Generated by/with" line. It quotes the same two lines, with a comment naming `rules.json` as the source.
- `stripFooter` in the hook is narrowed to the same exact block, and `prBody.footerStrippedByCi` is set to `true`. The pre-call body check stays strict: a session never writes the footer itself.
- Why: the hook runs before the proxy adds the footer; rewriting the body in CI causes another `edited` run; following each write with an MCP update was measured in #267 and the proxy re-adds it there too.

### 3.3 The client hook: early warning on the routes it reads

Kept narrow. Each item is cheap and fixes a measured false answer:

- **Create through `gh api` (F1).** A non-GET `gh api` on `repos/<o>/<r>/pulls` calls `checkPrCreate`, as `gh pr create` and the MCP tool already do. `ghApi` reads every field spelling (`-f`, `-F`, `--field`, `--raw-field`, with a space, with `=`, joined), `--input` and `--input=`, and treats a call with fields and no `-X` as a POST. One path normaliser (strip `?…` and a trailing `/`) is used by every pulls match.
- **Unreadable count.** An open count the hook cannot read refuses the create instead of allowing it.
- **Own branches only (Owner, 15:00 UTC; audit 4 R4).** The hook's open count uses the library's own-branch count, so fork pull requests are not counted.
- **Body files (F3).** A body file that does not exist yet, or that is written earlier in the same command, is refused with "write the body file in its own call first, then run this", never judged as the literal `@path`.
- **Reads (F5).** The PostToolUse body check runs only for writes (non-GET `gh api` on a pulls path, `gh pr create`, `gh pr edit`).
- **Docs exemption (F7).** `onlyRulesAndDocs` is removed from the limit check (Owner, 3.5).
- **Fail closed.** `create_pull_request` joins `GUARDED` and `MERGE_TOOLS_MATCHER` in `rules.mjs` and the fail-closed entry in `.claude/settings.json`.

### 3.4 The allowlist (replaces the round 2 tripwire and detective check)

A Bash command that writes to GitHub's API by any program other than a plain `gh` command is refused: "use `gh` directly, or the GitHub MCP tools". The hook refuses a command when its text contains `api.github.com` (any program but `gh`), `gh` anywhere but a program position, a program word that is a variable expansion, `gh alias set|import`, `gh pr revert`, or `gh api graphql` with a `mutation`. It refuses a non-GET `gh api` on `statuses/*` or `check-runs*`, since a session could otherwise write the required `pr-rules` status itself (audit 4 R1). It also refuses repository settings writes (audit 3 R5): a non-GET `gh api` on `branches/*/protection*`, `rulesets*`, `actions/workflows/*/(disable|enable)`, `actions/permissions*`, or `repos/<o>/<r>` itself, and `gh workflow disable|enable`, `gh ruleset` writes and `gh repo edit`. Anything it still cannot read is caught by `pr-rules` on GitHub (3.1). The client does not try to be complete; it only keeps the honest routes fast and the odd ones refused.
