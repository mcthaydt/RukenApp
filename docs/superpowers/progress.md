## Defect: the Worker ran out of memory (2026-11-14)

Fifth execution session of slice 2 (coordinator `session_01HNdX7JKYUteXqFnZHx6dez`), branch `fix/worker-memory` (pull request #68). "Received signal #6: Aborted" in the browser job, seen four times (runs 43578583711, 43579220096 twice, 43580392279), was workerd running out of memory. The cause was production code: `src/lib/server/db.ts` made a new Prisma client for every request, and each client that starts leaves memory behind in the Worker that `$disconnect()` does not give back. Cloudflare's limit is 128 MB per Worker, so the live site would have met this far sooner than a test run did.

- What the log said: workerd's own message, hidden by wrangler's log filter and printed once the sampler wrote to stderr (run 43580721057), was `V8 fatal error; location = Reached heap limit ... JavaScript heap out of memory`, then the abort. The app's workerd held 236 MB at the start of the journeys and 2.1 GB at the abort (about 800 requests), while its open files stayed flat at about 80, so it was not a connection pile-up.
- What it was not: the daily trigger (the abort came 5.0 seconds after the second "the daily trigger runs the job" journey in four runs, but four triggers in a row with the database asked every 250 ms did not abort, run 43580058126); a runner that was short of memory (12.5 GB free at the abort); Postgres (no connection errors in its log).
- What it was, measured in workerd on CI, 300 requests of each kind, growth of the app's workerd (runs 43581040363, 43581304011, 43581799963): no database work +0.1 MB per request; one Prisma query per request +2.8 MB; one query then `$disconnect()` +2.4 MB; a client that only connects +1.4 MB; a client made and never used +0.04 MB; a raw `pg` pool per request, ended or not, +0.17 MB; Prisma's own `pg` adapter with no client +0.1 MB; one shared client whose adapter sends each call to the running request's own `pg` pool +0.16 MB. On main with no journeys at all, about 1,000 requests with a client each made workerd abort in the same way.
- The fix: one Prisma client for the whole Worker, with an adapter (`requestScopedAdapter`) that sends every call to the connection the running request opened, opened on its first query and kept per request as before, so a request still never touches another request's connection. `databasePerRequest`, `prisma()` and `createPrismaClient` keep their signatures. Prisma gathers same-shaped `findUnique` calls from one tick into one batch and runs it for the first caller, who is still waiting, so that connection is alive.
- The tests: `tests/lib/server/db.test.ts` (four, on the adapter) and `tests/browser/worker-memory.test.ts` (300 requests that ask the database; it fails when the Worker's processes grow more than 250 MB, where a client per request grew about 835 MB). Red: run 43582206648 (verify failed on `not built yet` in the four new tests only, after lint and typecheck passed; the journey drove workerd to the abort). Green: run 43582428735 (verify, postgres and browser all pass; the memory journey passes in 3.2 seconds, 241 journeys passed and the one skipped is that journey's phone copy, which is skipped on purpose; no abort).
- Not tried and not needed: retries, longer timeouts, splitting the runs, skipping a journey.
- Branches `fix/workerd-abort` and `diag/workerd-abort-2` (the diagnostics, pull requests #65 and #67, both closed) are still on GitHub: this session cannot delete a branch through its proxy, so the merge session removes them.
