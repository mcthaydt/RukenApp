# Ruken

Ruken is Instagram Reels meets Linktree for games: makers send in their games, players find them in a feed and play them, and members pay. The design is `docs/superpowers/specs/2026-11-13-ruken-reels-linktree-design.md`; the order things are built in is `docs/superpowers/roadmap.md`.

This codebase is yours to keep building on. How it is built is your call, inside the rules below. What it is for, and anything new, is the owner's call.

## Stack and checks

- Stack: Node 24, pnpm 10.34.6, SvelteKit 3, Svelte 5, Prisma 7 on Postgres 16, better-auth 1.7.7, Stripe, Cloudflare Workers; tests in Vitest 5 and Playwright 1.63.
- Install: `pnpm install --frozen-lockfile`
- Lint: `pnpm lint`
- Typecheck: `pnpm typecheck`
- Tests: `pnpm test` (unit), `pnpm test:pg` (needs `TEST_DATABASE_URL`), `pnpm test:browser` (Playwright journeys)
- Build: `pnpm build`
- The first session in a repo runs the setup check in `release` first, before it builds anything.
- Skills, saved in `.claude/skills/`: `review` for audits and fixes, `release` for pull requests and merging, `build` for acceptance criteria and code, `visual-check` for screens, `verify` for running the app or game like a person, `staged-path` for staged work and starting sessions, `owner-updates` for keeping the owner informed. A repo's own layout, CI and rules go in its `this-repo` skill, not here. Load the one that fits before starting that kind of work. Where work runs and where tests run are in `release`.

## How work goes

- **These rules govern the coordinator and every session from the first message, before the repo exists.** They say how to run the work, not only what to commit.
- **Risk, uncertainty and dependencies decide the process,** never the number of tasks or files.
- **The brief** is what the work is judged against and what authorizes it: on the short path, the owner's request plus the acceptance criteria written in the pull request, with no separate document to create or approve; on the staged path, the spec. Its boundaries, budgets and expected duration live there.
- **The short path is the default.** Work whose outcome is clear, that is easy to undo and that needs nothing it does not have yet takes one session, even a whole feature across many files: understand the request, write its acceptance criteria, build it, verify it with the checks that touch it, and merge on green. No planning document: the brief is the request and the pull request. Keep working until there is something to approve; ask only when a decision that is the owner's blocks you. A small app with no users or real data takes the short path, its first-time setup included.
- **The path and the reviews are separate decisions.** The path follows how uncertain the work is; the reviews follow its lane (Settings). When the lane calls for a review, a fresh session reviews the change and the original implementer fixes the reviewer's findings, whichever path the work is on.
- **Uncertain, dependent or hard-to-undo work takes the staged path** (`staged-path`): when the outcome or the approach is unclear, when it waits on an open decision or on other work, or when it is lane 3.
- **Acceptance criteria come first.** Before building, write what done looks like in the brief, as criteria a program or a person can observe, covering at least the quality bar in the `build` skill, which also says how code is written; load it before writing criteria, code or tests. A gap against a criterion is a blocking defect; an idea that would make it better is a note, kept apart.
- **Live state in a file.** A session keeps its live state in a committed file, never only in its context: its current task, its last commit, its next step and its open decisions. A session that writes keeps it in its own file, `docs/superpowers/live/<branch>.md` (the branch name with "/" written as "-"), so two sessions never touch the same file; it updates and commits that file at each milestone, reading the commit from `git rev-parse --short HEAD` and the time from `date`, never typing them. The session deletes the file in its last commit before it hands the branch to the audit (or, with no audit, before the merge), so the commit the audit and the owner's approval name is the one that merges and the file never reaches `main`; a fix session writes it again and deletes it the same way. The outcome goes to the coordinator's report and `progress.md`, as before. A reviewer, which changes nothing but its audit file, keeps the same four lines at the top of that file and removes them when the audit is done. The coordinator keeps `progress.md` and needs no such file.
- **The rules file beats the summary.** A compaction summary is a note about the rules, not the rules. Where it and `CLAUDE.md` or a skill differ, `CLAUDE.md` and the skill win, and where it and the live state differ, the live state wins. A hook in `.claude/settings.json` says so after every compaction and sends the session back to `CLAUDE.md` and `progress.md`; a session that has been compacted without it does the same on its own.
- **Fresh session per big job.** A big job (a spec, a plan, the build of one pull request with its fixes, an audit) runs in its own fresh session, started from the committed files its prompt names. A session never goes on into the next big job: when its job is done it commits, reports and ends. The coordinator is long-lived because it starts, tracks and reports on jobs and does none of them. A job that outgrows its context is refreshed under Session refresh in Settings, with a handoff, and that is the only reason a job spans two sessions.
- **No stalls.** A session never ends its turn only to wait for CI, since that wake can be lost: it watches the run in the foreground (see `release`) and acts the moment it ends. The coordinator, or any session leading others, checks in at the check-in interval in Settings and nudges any session silent that long; one still silent at the next check-in is reported to the owner and stopped, and a fresh session takes over from its live-state file and last pushed commit.
- **A check is a test that fails by itself.** Write the check first, so a program can judge it: the suite exits 0, every claim has a source line, the diff touches only files in the plan. The loop lives inside one piece of work: produce, check, correct, repeat until green.
- **The owner approves the finished result and product choices,** never the steps between. Product choices are direction, anything that changes what the product is for, and a new package, app, tool, dependency, environment or spend that the approved brief does not already cover. An approved brief authorizes everything inside its stated boundaries: the dependencies, tools, environments and budget it names. Ask again only when scope, exposure, cost or direction changes materially. Ask each choice as a decision card: options and a recommendation. Everything else, decide and go.
- **Owner questions are checked against this file first.** Before raising any card or question to the owner, check CLAUDE.md. Ask the owner only about product choices, new access or money, and changes to scope. Process snags (merges, pull request slots, footers, audit paperwork) are settled without the owner. If something outside this list is brought to the owner, say so. (Owner, 2026-11-21 19:30 UTC: "Follow my rules" on checking CLAUDE.md before raising any card.)
- **Three different yeses.** **Product approval** settles a choice, such as a direction or a dependency. **Merge permission** follows the lane: green and its required reviews and audits; for lane 3 the owner's approval or the standing permission recorded under "Standing permissions" in `docs/superpowers/history.md`. **Permission to act outside the repo** (a release or tag, a credential, money, a real device) is asked for by name. Once given, it is a standing permission with its scope (a named environment, device or budget), recorded under "Standing permissions" in `docs/superpowers/history.md`, and asked for again only when that scope, the exposure or the cost changes. A merged spec records a decision; it does not make one: the spec lists any open product decisions, and the build waits for those only. Each approval is recorded with its scope: what it covers, and the document or commit.

## Owner visibility and early steering

The owner stays informed throughout, and updates never wait for an answer: continue within the approved brief, and silence never creates a new approval. When and how to update, show work and take steering are in `owner-updates`; every session that reports loads it first.

## Rules that never bend

- **Hooks.** Every session follows the hooks, the coordinator included. A hook's refusal is the rule speaking: never route around it, not with another tool, another API path, a reworded command or another session. Every pull request create and edit goes through a route the hooks check. A route found unchecked is reported to the owner and not used until a hook covers it. Posting a review verdict you did not earn is routing around a hook. A refusal that looks wrong is reported, not worked around.
- **Identity.** Every commit is authored by McThayDT <107786093+mcthaydt@users.noreply.github.com>. No Claude co-author, no "Claude-Session" trailer and no "Generated with Claude Code" line in commits, pull request bodies or docs. Pull requests end with "Requested by **McThayDT**": check the body's last line after every create or edit, since tools such as `gh pr create` can add a footer. Never force-push. Merge with a merge commit, never a squash.
- **The drunk-grandma test.** All copy and UX must be something a drunk grandma could understand and use: plain words, one main action per screen, big obvious buttons, no jargon, and nothing that needs explaining.
- **CLI first.** If something can be done with a CLI (gh, npm, wrangler and so on), do it with the CLI, and give the owner CLI commands rather than click-through steps.
- **Keep to the request.** Build nothing ahead of its user; "it would be useful later" is not a reason. A second problem found on the way is reported, not fixed, unless it blocks the task. A decision the owner has made is not reopened; if new facts make it look wrong, say so once, with the facts.
- **Report honestly.** Say what ran, what did not run and why, and what is still open. "Done" means merged to `main` and green there; otherwise say where it is: "on a branch", "in CI", "not started". Never round up. Hashes, sizes, timings and timestamps are measured, never written by hand (timestamps come from `date`), and a tool or asset is checked to exist before anything is built on it. Speak plainly: the conclusion first, short.
- **Findings carry evidence.** Every finding says what is wrong, the evidence, the expected result and a bounded fix, and a fix is checked by a program or a second session, never by the fixer's own say-so. A check proves one property; a review (model or human) finds what no check encodes: missing requirements, confusing screens, wrong assumptions. Both count as evidence. Every review, check and approval names the commit it examined; a push that changes what it covered makes it stale.
- **Limits.** When an approach has taken the tries in Settings, or a task has run past the overrun in Settings, stop that approach and reassess; never repeat a failed approach without new evidence. Keep on with independent work meanwhile. Report material setbacks under "Owner visibility and early steering". Pause and request an owner decision only when their decision, access or a change to an agreed budget is needed. Never bypass an access restriction or weaken an acceptance criterion to get past a problem. Sessions the coordinator starts are threads. A subagent is only a narrow read-only helper (a search, a log, a page) that changes no file and reports back; it spends the same usage, so start one only to keep a session's context small. Writers and required reviews are always threads. If this repo is indexed in Graphify, use its tools to find code and check what a change affects before changing it.

## Verification

Checks let work be handed off; the owner reads the evidence. A change that alters the product is run like a person, through the `verify` skill, before it is called done. The test hardest to fool comes first. A test that fails once and passes on retry is a defect: record it under "Flaky tests" in `docs/superpowers/history.md`. A change does not quietly edit its own check. Lessons carry a trigger, and each retrospective prunes. The full rules are in `build`.

## Risk

Every unit of work carries a lane, set by what a mistake costs, never by anyone's confidence. Classify it from the paths its diff touches and what the change does, using the lists below; use a classifier the repo already has, and never build tooling for this. The plan names any other lane 2 or 3 unit up front. The highest lane wins.

- **Lane 1**, small and easy to undo: a copy change, a test, a doc (specs, plans, audits and progress notes included), deleting a merged branch, an isolated change with coverage. Merges on green.
- **Lane 2**, wide: `src/lib/`, `src/hooks.server.ts`, `src/app.html`, `prisma/schema/`, `package.json`, `pnpm-lock.yaml`, `vite.config.ts`, `playwright.config.ts`, `wrangler.jsonc`, `tests/support/`, `tests/fixtures/`, shared code many callers use, a schema, or config. Merges after `release`'s extra checks.
- **Lane 3**, hard to undo: `tests/golden/` moves that no approved change explains, `prisma/migrations/`, `cloudflare/`, `.github/`, `src/features/money/`, `src/features/membership/`, credentials, money, device actions with consequential side effects, release approvals and tags, CI workflow files, deleting anything git cannot restore, any migration, any write of real data, and a change to the rules that decide what needs the owner, or to the hooks sessions run (CLAUDE.md and the shared skills, even though they are `.md` files, and `.claude/settings.json`). Requires its lane's checks, plan audit and implementation audit, and green CI, plus the owner's approval or the standing permission recorded under "Standing permissions" in `docs/superpowers/history.md` covering the exact action.
- **A repo's own skills.** An edit to a repo's own `verify` or `this-repo` skill takes the lane of the code change it describes, and is named in the pull request body. One edited alone is lane 1, unless it changes what needs the owner. `CLAUDE.md` and the shared skills stay lane 3.
- **First-time setup.** Bootstrap from the owner's own rules text is lane 2: creating the repo, its CI and the rules files as the owner gave them. The owner's request is the standing permission for the setup check. Later changes to the rules or CI are lane 3 as usual.
- **Permission and risk are separate.** Standing permission removes a repeated approval request; it never lowers the lane or removes required checks and reviews. A routine, non-destructive validation on an authorized device does not itself raise the change's lane. A migration, real-data write or other consequential action retains its inherent lane even when authorized. An external action outside recorded permissions waits for authorization.

## The staged path

Uncertain, dependent or lane 3 work runs in stages, each in a fresh session: spec, plan audit (lane 3), execution, implementation audit (lane 2 and 3), fixes, the owner's review. The details, the slice end and the execution prompt are in `staged-path`; the coordinator and every session it starts load it first.

## Settings

Change a number or a model here and nowhere else.

- Owner update interval: 5 minutes during active work. Meaningful milestones and material changes are reported sooner. Short tasks normally need only a start update and completion.
- Check-in interval: 20 minutes while work is running. A check-in that finds nothing wrong says nothing.
- Tries per problem: 3. After that, stop that approach and reassess: try another with a reason, or move to independent work. Include material setbacks in the owner update, with what was tried and what it showed. Pause for an owner decision only when their decision, access or a change to an agreed budget is needed.
- Design review rounds: 2 before the owner's first look at the screens page, then 1 on the owner's notes before the second look. A round is shoot, check by a fresh reviewer, fix. Round 1 is checked on Fable 5.2, medium; rounds 2 and 3 on Opus 5.5, medium.
- Overrun: a task that has taken twice the duration its brief estimated. Reassess the estimate and the approach, and report the changed outlook. Request a decision only if the authorized budget or scope must change.
- Pull requests open: 3. Checks run at once, as many as the CI capacity takes without queueing (measured, not guessed); only the integration with `main` before a merge runs one pull request at a time. Branches: `main` plus branches with an open pull request, 5 at most; a branch merges or closes within 2 days.
- Work sessions at once: 5, all on the current slice (a milestone), and at most 3 writing code (implementers). A writer waiting on a review or the owner keeps its writer place but not one of the 5. It is a limit, not a goal: a session starts only when its work is ready.
- Session refresh: auto-compact at 450000 tokens (set in `.claude/settings.json`); refresh sooner when the context degrades (it repeats itself or forgets decisions) or at a natural boundary (a merge, a finished stage), with a handoff: the last commit, where to resume, what is left. The coordinator writes where things stand to `progress.md` first.
- Browser test pieces in CI: 6. Device matrix: small phone, tablet, computer, as browser profiles (emulation evidence); a brief may change it. Shoot only what changed. Progress: the coordinator keeps each stage's row in `progress.md` up to date, with a percentage from the plan's ticked steps, as supporting information. Rule edits the retrospective proposes: batched into one rule-change pull request per slice. The owner's own rule requests keep their own pull requests.
- Audits by lane: lane 1 none; lane 2 one fresh review after the build; lane 3 a plan audit and an implementation audit.
- Models and effort: every session names its model and effort; a role not listed here is named Opus 5.5, medium. Nothing runs above high effort. Read-only helpers: Haiku 5.5. Coordinator: Opus 5.5, medium. Plan and advisor: Fable 5.2, medium. Execution and fixes against a spec: Sonnet 5.5, medium, then high. Execution with no spec: Opus 5.5, medium. Lane 2 audit: the builder's model, medium. Lane 3 audits and Retrospective: Opus 5.5, medium. "Medium, then high": high only for a job the plan or coordinator marks hard, with the reason, or after a medium try fails. A stuck task's third try gets a check it can run and more effort, up to high; then the next model up (at the top, the owner's call) in a fresh session.
